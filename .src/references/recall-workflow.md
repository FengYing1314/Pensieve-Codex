# Pensieve Recall Workflow

Use this workflow when project memory can narrow the current question or broad source exploration.

1. Locate relevant project memory. A nearby `.pensieve/` is a retrieval candidate, not evidence of ownership or write authorization. For cross-project work, keep each fact associated with its actual project.
2. Read `.pensieve/state.md` when useful and consult the generated graph only when it narrows the search. Missing or stale state is a reason to read original files and source, not to run maintenance during a read-only task.
3. Reuse relevant file locations, call chains, and verification paths. Check facts against current evidence; keep confirmed decisions and maxims within their recorded scope and the current request. A pipeline cannot grant permission or broaden the requested work.
4. Check actual source paths and status after following graph links. Short-term entries are draft evidence; the graph shares target-layer IDs and can omit aged entries. Search the original long-term and short-term directories when checking duplicates, conflicts, or freshness.
5. Read at most five likely entries. If needed, perform at most two targeted searches and at most ten total recall operations, returning to source sooner once the question is answered. These are ceilings, not a required itinerary.

Return a compact briefing with evidence paths and unresolved questions. Do not write memory during recall. A later, authorized implementation task may use the enabled automatic capture policy; explicit maintenance follows its own requested scope.
